## 一、项目基本信息与 30 秒电梯演讲

- **项目名称**：跨境电商多 Agent 选品调研与人工审批工作台（`ecom-selection-multiagent-studio`）
- **项目属性**：基于本人在杭州宠品家跨境宠物电商真实选品评审流程的深度抽象与工程重构，独立设计、编码并评测的**个人开源多 Agent 工程项目**（与项目一 RAG、项目二 NL2SQL 同属宠物跨境电商垂直域，形成完整矩阵）。
- **技术栈**：Python 3.12、`FastAPI`、`LangGraph`、`ThreadPoolExecutor`、`PostgreSQL 16`（`ecom_selection` 任务与多版本 Diff 存储）、`Redis 7`（任务防重与并发上限锁）、`Langfuse v2`、`DeepSeek`、`pytest`
- **30 秒电梯演讲**：
  > 跨境电商新品立项前，运营需要同时看竞品价格规格、扒几百条买家差评、再写选品报告给老板评审，传统单轮大模型汇总特别容易混进配件拉低均价、凭几条评论瞎猜市场、甚至编造价格和引用。我设计了这套多 Agent 选品工作台：先用规则+相似度排除配件并检测样本缺口，再让市场分析 Agent 和用户洞察 Agent 并行独立取证（串行 5106ms 降到并行 2217ms，降延 56.6%），由运营决策 Agent 起草报告、证据审核 Agent 硬核验引用与价格区间（违规自动打回重写 1 次并生成版本 Diff）；若存在样本缺口或二次审稿不过，自动挂起进入 Human-in-the-Loop 人工审批门禁，运营在中文工作台批注后恢复执行并导出最终 Markdown 报告。

## 二、业务场景与多 Agent 分工设计

### 为什么需要多 Agent 而不是一个超级 Prompt？
1. **统计事实与主观评论物理隔离**：如果把商品列表和零散评论一起塞给单个 Prompt，模型很容易被几条高情绪差评带偏，或者凭零星评论瞎猜价格带。拆成 **市场分析 Agent（只看结构化统计 `M1..Mn`）** 与 **用户洞察 Agent（只看可比竞品评论 `Rxxxx`）** 后，职责清晰且可真正并行执行（实测耗时从 `5106 ms` 降至 `2217 ms`，**降延 56.6%**）。
2. **起草与审核角色分离（Generator vs Auditor）**：让生成报告的模型自己检查自己极易“放水”；把 **证据审核 Agent** 设计为**确定性硬核验引擎**（正则提取 `[M*]`/`[R*]` 核对证据池 + 价格带越界检测 + 4 章节完整性校验 + 样本缺口强制披露检查），能 100% 稳定抓出伪造引用（如 `[M999]`、`[RFAKE01]`）和离谱报价（如 `$999`）。
3. **Human-in-the-Loop（HITL）人工兜底**：AI 选品报告涉及真金白银的开模和备货决策，绝不能在样本量严重不足（例如冷门类目“宠物智能恒温烘干箱”仅找到 1 款竞品）时自动放行。系统自动将任务挂起为 `awaiting_human_review`，持久化到 PostgreSQL，等运营批注（批准 / 附要求修订 / 驳回）后恢复工作流并生成 Unified Diff，实现真正可交接、可追溯的企业级评审流程。

## 三、核心实测指标与工程亮点

1. **可比竞品筛选与缺口预警（`screening.py`）**：
   - 在饮水机调研场景中，精准入选 4 款主商品，100% 剔除 2 款共用关键词的配件（替换滤芯、通用水泵）与 1 款缺价格/规格的脏数据；
   - 在烘干箱调研场景中，识别到仅 1 款可比竞品（低于门槛 3 款）和 2 条评论（低于门槛 4 条），自动生成样本缺口告警并强制挂起 HITL 审批。
2. **双路 Agent 并发加速**：`ThreadPoolExecutor(max_workers=2)` 并行调用市场 Agent 与用户洞察 Agent，端到端研究耗时从串行 **`5106 ms`** 降至 **`2217 ms`（-56.6%）**。
3. **审核打回重写 + 版本 Diff 闭环**：
   - 注入包含 4 项违规（伪造 `[M999]`/`[RFAKE01]`、异常高价 `$999`、缺合法证据引用）的 V1 首稿后，证据审核 Agent 100% 检出全部 4 项问题并自动打回重写；
   - 决策 Agent 吸收审稿意见重写生成 V2 后 100% 通过审核，系统自动生成 **59 行 Unified Diff** 供运营对比修改前后差异。
4. **HITL 挂起恢复与任务治理**：
   - 烘干箱任务自动挂起 `awaiting_human_review` → 运营提交修订批注（要求补充采购 2 台样机实测噪音与温控曲线）→ 系统恢复执行生成 V2 定稿（状态转为 `approved`，生成 9 行 Diff）并同步上报 Langfuse `human_approval` Score；
   - 基于 Redis 原子锁实现同主题任务防重复提交与最大并发上限控制（`MAX_CONCURRENT_TASKS=3`），实测并发重复提交 100% 拦截并返回已有 `task_id`。

## 四、高频面试追问标准应答库

**Q1：证据审核 Agent 为什么用确定性规则代码而不是再调一次 LLM-as-a-Judge？**
> 答：核心原因是**稳定性、延迟和成本**。引用编号是否在证据池内、价格是否严重偏离竞品统计区间、是否包含 4 个必需章节、有样本缺口时是否明确提示风险——这些都是高确定性约束，用 Python 规则 1ms 内就能做到 100% 零漏检且 0 Token；只有在审核更主观的文案质量或离线评测时才引入 LLM-as-a-Judge。生产系统里凡是能用确定性护栏拦住的，绝不把生死交给模型概率。

**Q2：为什么审核不通过只允许自动重写 1 次，而不是无限循环直到通过？**
> 答：这是多 Agent 工程里非常关键的**防死循环与成本熔断设计**。如果证据本身缺失或者指令存在内在冲突，无限重试会让 Agent 陷入死循环狂烧 Token 且拖死接口。设上限为 1 次（`MAX_AUDIT_REWRITES=1`）：能靠明确审稿意见修正的格式/引用错误 1 次就能修好；若重写后依然不过，说明属于硬边界问题，必须立刻熔断并挂起转人工复核（HITL），把异常暴露给运营而不是掩盖。

**Q3：你的 Human-in-the-Loop 人工审批是怎么落地的？服务重启后挂起的任务会丢吗？**
> 答：不会丢。我把每个调研任务的上下文、竞品筛选审计清单、结构化证据池（`market_evidence` / `user_evidence`）、节点耗时、审稿问题以及所有历史报告版本（`report_versions`）全部持久化在 PostgreSQL `ecom_selection` Schema 中。任务进入 `awaiting_human_review` 后立即释放 Redis 执行槽位，运营哪怕隔天在前端工作台或通过 `POST /api/v1/tasks/{task_id}/review` 提交审批/修订意见，都能从数据库恢复完整证据上下文继续执行并生成新版 Diff。

**Q4：三个项目合起来，你认为自己最大的竞争优势是什么？**
> 答：第一是**垂直领域闭环一致性**——三个项目全部锚定我真实干过的跨境宠物电商领域，分别打通了“非结构化评论查证（Agentic RAG）”“结构化经营数仓与异常排查（NL2SQL + 并发归因）”“新品立项多 Agent 协作与人工审批（Multi-Agent + HITL）”，能把业务痛点直接翻译成工程架构；第二是**全链路可量化、可观测、可迭代的工程习惯**——每个项目都有 V1 vs V2 实测评测集、真实踩坑复盘、Redis 防重/缓存、Langfuse 监控和纯中文演示台，不是只停留在调 API 跑通 Demo 的阶段。
